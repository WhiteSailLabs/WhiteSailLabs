# Local Asset Navigator｜让散落资料重新进入工作流

> 公开复现版 · 用公开仓库替代私人项目目录

[English](local-asset-navigator.md)

## 真正的问题不是“文件太多”

项目做久以后，资料会自然散开：需求写在 Markdown，讨论留在会议记录，架构图藏在截图目录，最终交付和几个 `final-v2` 混在一起。用户往往记得“以前做过类似方案”，却说不出文件名和位置。

传统搜索要求用户先知道关键词。可真实任务通常是“找出上次提交给客户的版本”“把这个项目对应的架构图和说明放在一起”。这不只是全文检索，还涉及版本、项目关系、文件用途和访问权限。

更麻烦的是，资料越重要，越不能为了方便搜索就默认上传到外部服务。因此我把目标定义成一个本地优先的资料导航器：只读取用户明确允许的目录，给出文件位置和命中原因，遇到多个版本时让人确认，而不是擅自宣布哪个是最终版。

## 我先画清楚资料怎么被使用

我把常见查找过程拆成四步：用户记得什么线索、通常先去哪找、怎样判断版本、找到后还要和哪些文件一起使用。由此确定第一版需要保留的不只是正文，还包括路径、标题、文件类型和文件之间的引用。

公开复现版没有扫描私人硬盘，只以这个 GitHub 主页仓库作为测试目录。20 个任务覆盖中英文主页、四篇案例以及带“项目”等干扰词的表达。这样既能公开复跑，也能验证一个现实问题：同一主题经常同时出现在主页摘要、案例正文和工具代码中。

隐私边界从一开始就写进方案：目录采用白名单；索引和查询记录保存在本机；工具目录、缓存和生成结果应与用户资料分开；未来即使调用外部模型，也只发送当前任务需要的最小片段。

## 第一轮：搜索器被自己的代码骗了

第一版遍历仓库文本文件，读取路径和正文，再按查询词出现次数排序，路径命中给予更高权重。它没有向量数据库，也没有大模型，是一个用于暴露问题的最低成本基线。

20 个任务只命中 **6 个**。

失败很有代表性。搜索“本地资料搜索”时，评测脚本因为写着这句话，反而可能排到第一；搜索某个项目时，包含全部项目名称的主页摘要会压过项目自己的案例页。系统只知道词出现了几次，不知道“这是工具代码”“这是目录页”“这才是交付正文”。

这说明检索失败首先是资料治理问题。若不区分内容角色，换成更复杂的相似度模型也可能把噪声找得更准。

## 第二轮：先划边界，再提高相关性

我先排除实验代码和结果目录，只保留真正需要导航的资料；随后把标题命中的权重提高，因为标题通常比正文中的偶然提及更能代表文件用途。

最终可复现结果提升到 **9/20**。提升有限，却明确了下一步方向：当前方案仍无法理解“中文主页”和 `README.zh-CN.md` 的关系，也无法判断主页中的项目链接与项目正文谁更应该排在前面。

因此下一版不会只加入“语义搜索”四个字，而会增加分层索引：标题、路径、正文、出链、被引用关系和版本状态分别计分；工具文件默认降权；用户确认过的版本关系作为显式事实保存。

## 产品形态：结果必须让人敢点开

一个可用结果不应只有文件名。它需要显示完整路径、匹配到的标题或正文片段、文件类型、修改时间、相关版本，以及为什么排在这里。如果存在两个“最终版”，系统应该并排展示差异和引用记录，请用户确认。

用户的确认不能只服务当前会话。它应形成一条本地关系，例如“文件 A 是项目 X 的交付版本，文件 B 是草稿”，下次查询继续使用。这样工具才会随着实际工作逐渐变准，而不是每次重新猜。

权限同样是产品功能。无权限目录不能进入索引；删除索引必须能够真正清除本地记录；搜索日志不应泄露用户没有主动选择的资料。

## 这个项目留下了什么

公开仓库保留了索引边界、搜索代码、20 条任务、逐条结果和失败清单。当前 9/20 并不好看，但比一个无法复现的“智能文件助手”演示更有用。

这次实践沉淀了四条判断：

1. 搜索质量从资料边界开始，而不是从向量数据库开始。
2. 工具代码、摘要页和正式资料必须在索引中拥有不同角色。
3. 版本关系需要人确认，系统不能根据文件名擅自决定。
4. 本地优先不只是部署方式，还包括权限、日志和可删除性。

当前公开版还没有处理 PDF、图片、OCR、重复文件和真实版本冲突。下一阶段会先把文本任务做到稳定，再加入多模态索引，并用实际查找时间和错误版本率评估是否真正减少工作。
